## Project state

Front end of the tutoring marketplace described in the SRS (Online / Physical Tutoring Platform, v1.0). Built so far: the home page (`/`), the tutor request form (`/request-a-tutor`, plus `/success`), the How It Works page (`/how-it-works`, covering both the parent and tutor journeys), the Concierge Matching page for parents (`/tutor-request`), the Subjects page (`/subjects`, a client-side searchable catalogue built from `subjectCategories`, with display copy in `lib/constants/subjects-page.ts`; its cards link to `requestSubjectHref(subject)`, which pre-fills the request form's subject via `?subject=`), the Contact page (`/contact`: details from `siteConfig.contact`, and a single-step react-hook-form + zod form with the server action `app/[lang]/contact/actions.ts` and service `lib/services/contact.ts`, which shows its success state inline), the FAQ page (`/faq`: questions in `lib/constants/faq.ts` with `**bold**` markup, a client-side search/filter accordion, and FAQPage JSON-LD), the Education Levels page (`/education-levels`: one section per stage, whose ids match `educationLevels` in the taxonomy and double as `#` anchors; copy in `lib/constants/education-levels-page.ts`), the About Us page (`/about`, copy in `lib/constants/about.ts`), the Blog (`/blog` and `/blog/[slug]`: copy in `lib/constants/blog.ts`, articles in `lib/constants/blog-posts.ts`, which pages read only through `blogPosts` / `getPostBySlug` / `featuredPost` as the seam for a future CMS; the newsletter signup is the server action `app/[lang]/blog/actions.ts` with the stub `lib/services/newsletter.ts`, and the Arabic is in `lib/i18n/ar/blog.ts` and `blog-posts.ts`), the SEN Tutors in Dubai SEO landing page (`/sen-tutors-dubai`: copy in `lib/constants/sen-tutors.ts`; use "Special Educational Needs (SEN)" wording, never "autism", in copy, routes and imagery, which deliberately makes no claims about tutors, outcomes or availability; FAQPage JSON-LD; linked from the footer), the tutor recruitment page (`/become-a-tutor`), the tutor registration form (`/tutor-registration`, plus `/success`) and a shared header and footer. There is deliberately **no public tutor directory**: `/tutors/*` and `/find-a-tutor` redirect to `/request-a-tutor` (`next.config.ts`, which also sends the old `/tutor-request/success` to `/request-a-tutor/success`), and every "I Need a Tutor" / "Request a Tutor" button uses `requestHref` (`lib/constants/site.ts`). Every page is also served in Arabic at `/ar/...` (see i18n below). Other routes linked in the navigation and footer (`/reviews`, `/privacy`, `/terms`, `/academic-integrity`) don't exist yet. No database or auth is wired up; form submissions are emailed instead (see "Form submissions & email" below). The SRS says all stats, ratings, reviews and tutor records are placeholders to be replaced with approved data.

## Stack notes

- **Next.js 16.3 App Router** with React 19.2 and strict TypeScript. The APIs differ from older Next.js (see AGENTS.md). The bundled docs are in `node_modules/next/dist/docs/01-app/` (`01-getting-started`, `02-guides`, `03-api-reference`). Read the relevant page before using routing, caching, data fetching, `proxy` (the replacement for middleware), or metadata APIs.
- Route props use the globally generated helper types (for example `LayoutProps<"/[lang]">` in `app/[lang]/layout.tsx`, and `PageProps<"/[lang]/...">` for pages). These come from `.next/types` and are created by `next dev` / `next build`.
- **Tailwind CSS v4** is configured in CSS, not in a `tailwind.config` file. It is loaded through `@tailwindcss/postcss` (`postcss.config.mjs`), and theme tokens live in `app/globals.css` (`@import "tailwindcss"` plus `@theme inline`, which maps CSS variables such as `--background`/`--foreground` to utilities). There is no dark mode; the site is light-only.
- The Plus Jakarta Sans font is loaded with `next/font/google` in the root layout (`--font-jakarta`). Brand colour tokens (`brand-*`, `ink`, `muted`, `lavender`, `night`) are defined in `app/globals.css`.
- Path alias: `@/*` maps to the repo root (there is no `src/` directory). Shared domain types live in the root `types/` directory (for example `types/tutor.ts`). Compose class names with `cn()` (`lib/utils/cn.ts`, clsx + tailwind-merge).
- Scroll-in animation goes through `Reveal` (`components/ui/reveal.tsx`, framer-motion). It respects reduced motion and renders the same markup on server and client to avoid hydration mismatches, so use it rather than animating directly in sections. The root layout wraps everything in `MotionProvider` (`LazyMotion` with `strict`, features lazy-loaded from `lib/motion-features.ts`), so import `m` from framer-motion, never `motion` (it throws under strict mode). Separately, `ScrollAnimations` (`components/ui/scroll-animations.tsx`, mounted in the layout) fades in every below-the-fold `main section` and `main .grid > *` after each navigation using the `.rv` / `.rv-in` classes in `globals.css`; it skips forms, `Reveal`-managed elements and anything inside `[data-no-rv]`, so add that attribute to opt a block out. Other shared primitives (`ButtonLink`, `SectionHeading`, `Eyebrow`, `SegmentedControl`) are in `components/ui/`.

## Architecture notes

- **English / Arabic (i18n):** every route lives under `app/[lang]/` (root layout included; `generateStaticParams` gives `en` and `ar`). `proxy.ts` rewrites unprefixed URLs to `/en/...`, serves `/ar/...` as-is and redirects `/en/...` to the unprefixed URL, so English keeps its old URLs. Redirects in `next.config.ts` are declared for both prefixes. The layout sets `lang` but keeps `dir="ltr"` for every language (the layout never mirrors; `localeDir` in `lib/i18n/config.ts`); Arabic glyphs fall back to IBM Plex Sans Arabic via `--font-sans`, and `globals.css` neutralises letter-spacing in RTL.
  - Translation is gettext-style: **the English copy is the key**. Constants in `lib/constants/*` stay English; the Arabic lives in `lib/i18n/ar/*.ts` (one dictionary per page, plus `common` and `forms`). A new page dictionary must be added to the merged `arDictionary` in `lib/i18n/ar/index.ts`; because the dictionaries are merged, an English string has exactly one Arabic translation site-wide. Missing keys fall back to English, so after changing or adding English copy, add the Arabic and run `npm run i18n:check`. The check (`scripts/i18n-check.mjs`) skips copy-object keys such as `id`, `href`, `icon`, `keywords` (see its `SKIP_KEYS`) and the brand name, so put non-display values under those keys.
  - Server Components: `const t = await getT()` (`lib/i18n/server.ts`, reads the `lang` root param). Client Components: `const t = useT()` (`lib/i18n/client.ts`), which only ships `common` + `forms`; a client component rendering page copy passes that page's dictionary (`useT(faqDictionary)`), and `i18n:check` flags client strings missing from those. `t("… {name}", { name })` interpolates; `t.deep(obj)` translates every string in a copy object except ids/hrefs/images.
  - Never translate stored values: form option `value`s and taxonomy subject names are submitted in English and only translated for display. Validation messages stay English in the zod schemas and are translated at display time (`FieldError` → `lib/i18n/validation.ts`, which also handles the `text()` templates).
  - Links: use `Link` from `components/ui/link.tsx` (and `ButtonLink`), which prefixes `/ar`; the wizards' success redirect uses `localizeHref`. The EN/AR switcher is `components/layout/language-switcher.tsx`, fixed below the header.
  - Arabic text: the page layout is identical to English (LTR); only text blocks read right-to-left, via the `[lang="ar"] … { unicode-bidi: plaintext }` rule in `globals.css`. Because `dir` is never `rtl`, `rtl:` variants and `locale === "ar"` layout switches do nothing, so do not add new ones.

- **Content & taxonomy:** `lib/constants/taxonomy.ts` holds the SRS §9 subjects, education levels and curricula; forms, filters and matching all reference these ids. Page copy and placeholder marketing figures live in `lib/constants/*` (each file's header comment flags the PLACEHOLDER claims that the business must confirm, citing the SRS section). Marketing pages follow one pattern: `app/[lang]/<route>/page.tsx` exports `generateMetadata` (translated titles) and stacks section components from `components/<page>/sections.tsx`, which read their copy from the matching constants file. Tutor records are placeholder data in `lib/data/tutors.ts` (read via `lib/services/tutors.ts`, the seam for a future database).
- **Multi-step intake forms:** both wizards follow the same pattern, built on `useMultiStepForm` (`lib/hooks/use-multi-step-form.ts`). The hook runs a single react-hook-form instance across all steps. Its resolver swaps in the zod schema for the active step, and the last schema validates the whole form. It also saves drafts to localStorage ("Save Draft"; fields in `transientFields` are left out), manages focus between steps, and handles the server action's `SubmitResult` (a type exported from the hook, which the contact action also returns): `fieldErrors` are routed back to the step that owns each field (the `stepFields` arrays). Each form has:
  - a validation module in `lib/validations/` that exports the per-step schemas, the step→field map, the defaults and a full schema. The server action in `app/[lang]/<route>/actions.ts` re-validates with the full schema, which is the authoritative check. Shared zod helpers (text, phone, email, subject values) live in `lib/validations/common.ts`.
  - step components in `components/forms/<form>/`, with shared UI in `components/forms/wizard-parts.tsx`, `fields.tsx`, `availability-fields.tsx` (the day/time grid both wizards use) and `subject-combobox.tsx`. The shared option lists (`phoneCountryOptions`, `dayOptions`, `timeWindowOptions`, upload limits) live in `lib/constants/tutor-request.ts` even though the registration and contact forms import them too.
  - a persistence service in `lib/services/` that generates a reference id and emails the submission (see below). There's no database or object storage, so uploads keep file metadata only.
  - a versioned `draftKey`, set in the wizard component (`components/forms/<form>/*-wizard.tsx`). **Bump it when the step structure changes**, or stale drafts will restore into the wrong steps.
  - optional `overrides`: values that always win over a restored draft. The request page checks `?subject=` against the taxonomy and looks up `?tutor=` with `getTutorById`, and the wizard passes both in as overrides (`subject`, `requestedTutorId`).
- **Form submissions & email:** `lib/services/notify.ts` (nodemailer over Gmail) has `notifyTeam`, which emails every submitted field to `siteConfig.contact.email`, and `sendConfirmation`, a best-effort receipt to the submitter. The request, registration and contact services call both. It reads `GMAIL_APP_PASSWORD` (a Google app password) and optional `GMAIL_USER` (defaults to the inbox) from `.env*` (git-ignored; copy `.env.example` to `.env.local`). Without the password, dev logs the submission to the console, but in production `notifyTeam` throws so the submission fails instead of being lost. The newsletter service is still a stub.
- **Tutor request (`/request-a-tutor`):** a single step (`RequestStep`): full name, relationship, email (optional, but required when the contact method is email, via `superRefine`), phone, grade/year (`levelOptionValues` from the taxonomy), emirate (`emirateOptions`), curriculum (`requestCurriculumOptions`, whose values are taxonomy curriculum ids), preferred contact method and consent. The schema is in `lib/validations/tutor-request.ts` (`subject` / `requestedTutorId` are optional hidden values from `?subject=` / `?tutor=`), with `lib/services/requests.ts` as the persistence service. The six-step `requestSteps` constant is no longer a form; it only feeds the FAQ blueprint. The sidebar copy is in `lib/constants/request-page.ts`.
- **Tutor registration (`/tutor-registration`):** 5 steps (Personal → Teaching → Availability → Pedagogy → Review), defined in `lib/validations/tutor-registration.ts`, with `lib/services/tutor-applications.ts` as the persistence service. Copy and options are in `lib/constants/tutor-registration.ts`. The marketing page `/become-a-tutor` (`components/become-tutor/sections.tsx`) links to it.
